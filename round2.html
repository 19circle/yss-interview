01会计地基（15 分钟速成，必须张口就来）

不用学会做账，但要能听懂账、说清方向。

1.1 三条铁律

① 会计恒等式

资产 = 负债 + 所有者权益
基金产品里，所有者权益就是投资者持有的份额对应的净值。任何一笔业务发生后，这个等式必须仍然成立。

② 借贷记账规则

有借必有贷，借贷必相等
每笔业务至少影响两个科目，借方合计 = 贷方合计。这是账务模块测试的第一条检查规则。

③ 科目的借贷方向

资产类：借增贷减
负债类：贷增借减
所有者权益类：贷增借减
损益类：收入贷增、费用借增

1.2 基金会计科目表（记名称和类别，不要报编码）

类别常见科目说明
资产类 银行存款、清算备付金（结算备付金）、存出保证金、证券投资（股票/债券/基金投资）、买入返售金融资产、应收股利、应收利息、其他应收款、待摊费用 产品能变成钱的东西。证券投资下一般分"成本"和"估值增值"两个明细。
负债类 卖出回购金融资产款、应付赎回款、应付管理人报酬、应付托管费、应付销售服务费、应付交易费用、应交税费、其他应付款、应付收益（应付利润） 产品欠别人的钱。应付管理人报酬/托管费/销售服务费是估值系统里最常考的计提科目。
所有者权益类 实收基金（实收资本/份额）、未分配利润、损益平准金 损益平准金是基金会计特有的，用于区分申赎带来的份额变动和真实投资收益。
损益类 投资收益、公允价值变动损益、管理人报酬、托管费、销售服务费、交易费用、利息收入、其他收入 影响当期利润的科目。期末要结转到未分配利润。
⚠️ 重要提醒：不要说科目编码 各家公司（甚至同一家公司不同产品线）的科目编码体系都不一样，你报编码就是给自己挖坑。 标准安全答法："科目名称是行业通用的，编码我在原公司的体系里记得，但不同公司会不一样，所以我一般记名称和类别。"

1.3 一句话把"做账"讲清楚

背下这段话 "做账就是：把每天发生的业务，按会计规则翻译成会计分录，记到明细账里，汇总出科目余额表，再往上生成财务报表。估值系统里的做账还有一个特点——它是业务驱动、自动生成凭证的，业务数据一变，凭证就得跟着变，所以我做测试的重点是验证'业务数据 → 凭证'这个翻译过程对不对，而不只是看界面能不能操作。"

02做账链路全图（复试最可能让你讲的）

图 1：做账链路与测试验收入口

这条链路上，测试该验什么

环节验证点
① 业务发生业务数据本身是否完整、准确、不重复（数据接入的幂等性）
② 生成凭证重点借贷方向对不对、科目选得对不对、金额算得对不对、借贷是否平衡、一笔业务是否重复生成凭证（凭证重复是高频缺陷）
③ 过账凭证是否完整过到明细账/总账；同一科目多笔业务累加是否正确
④ 试算平衡全部科目借贷合计是否相等；不相等时能不能定位到具体凭证
⑤ 期末结账损益结转是否完整、结账后能否反结账、跨月跨年是否正确
⑥ 科目余额表期初余额 + 本期借方 − 本期贷方 = 期末余额，逐科目核对
⑦ 财务报表报表项目和科目余额的勾稽关系是否成立（如资产合计 = 负债 + 权益）
⑧ 估值表与估值计算、与托管行核对结果一致

04实战题："科目余额表借贷不平，你怎么查？"

这是账务模块最高频的实战题。按下面这条路径答，条理清楚就够了。

图 2：借贷不平的五步排查路径

四类高发原因（记住这个，面试能撑住）

原因表现怎么验出来
① 单边分录只生成了借方或只生成了贷方查借贷金额相等的凭证数量，与业务笔数比对
② 重复生成同一笔业务生成了两张凭证按业务唯一键（产品+日期+流水号+业务类型）分组计数，找 count > 1
③ 精度截断金额四舍五入后借贷差 0.01核对小数位和舍入顺序；用 ROUND 归一到业务精度再比
④ 期初未结转上期期末余额没有成为本期期初核对上期期末 = 本期期初，逐科目比

可以现场甩出来的 SQL

-- 找重复生成的凭证（同一业务唯一键出现多次）
SELECT fund_code, biz_date, biz_serial, biz_type, COUNT(*) AS cnt
FROM   t_voucher
GROUP BY fund_code, biz_date, biz_serial, biz_type
HAVING COUNT(*) > 1;

-- 逐凭证校验借贷是否平衡
SELECT voucher_id,
       SUM(CASE WHEN dc_flag = 'D' THEN amount ELSE 0 END) AS debit_amt,
       SUM(CASE WHEN dc_flag = 'C' THEN amount ELSE 0 END) AS credit_amt
FROM   t_voucher_entry
GROUP BY voucher_id
HAVING ROUND(SUM(CASE WHEN dc_flag = 'D' THEN amount ELSE -amount END), 2) <> 0;

-- 科目余额表勾稽：期初 + 借 − 贷 是否等于期末
SELECT fund_code, subject_code, beginning_balance, debit_amount, credit_amount, ending_balance
FROM   t_subject_balance
WHERE  ROUND(beginning_balance + debit_amount - credit_amount, 2)
       <> ROUND(ending_balance, 2);

表名是我按常见设计假设的，被问到时说明"表名我不清楚，我说一下思路"即可。重点是把三张校验 SQL 的思路讲清楚：重复检测、单笔借贷平衡、余额勾稽。

05复试 14 题（账务方向）

必答 是几乎一定会问的，必须张口就来。

业务与账务

必答说一笔买入股票的业务，从成交到生成凭证的完整链路。

分四步：① 业务数据进来——从投资交易系统或交易录入获取成交明细，包括证券代码、数量、成交价、费用；② 数据校验——校验证券主数据是否存在、数量金额是否合理、有没有重复；③ 生成凭证——按规则生成"借：证券投资—成本 + 交易费用，贷：证券清算款"；④ 过账与汇总——凭证过到明细账，汇总到科目余额表，最终进入估值表和财务报表。

补一句我的测试思路："我会重点验第 ③ 步，因为它是最容易出问题的翻译环节——借贷方向、科目选择、金额拆分（成本和费用怎么分）、以及会不会重复生成。"

必答估值表里的"成本"和"市值"分别怎么来？差额叫什么？

成本来自账务系统里证券投资的成本余额——按移动加权平均法结转后的持仓成本。市值 = 持仓数量 × 估值日的估值价（股票的收盘价 / 债券的第三方估值净价 / 场外基金的公布净值）。差额叫估值增值，也就是浮动盈亏，等于"市值 − 成本总额"。它每天随行情变动，系统按变动额记录，并生成公允价值变动损益的凭证。

必答管理费、托管费怎么计提？凭证怎么写？坑在哪？

按日计提：每日费用 = 计提基数 × 年费率 ÷ 365（部分产品用 360，看合同）。

分录：借"管理人报酬（或托管费）"，贷"应付管理人报酬（或应付托管费）"。

坑有四个：① 计提基数用当日还是前一日净值；② 天数口径自然日还是交易日，节假日是否计提；③ 费率是否分段、有上下限；④ 起止日期——成立首日、终止日、暂停估值期间是否计提，以及费率变更的生效日切换。

必答科目余额表借贷不平，你怎么查？

用第 04 节的五步路径 + 四类高发原因。要点是先缩小范围（全局还是局部、差额多少），再用差额反查凭证，最后落到 SQL + 代码 + 日志三层定位。

高什么是损益平准金？为什么基金会计要有这个科目？

作用是区分"申赎带来的份额变动"和"投资产生的真实损益"。投资人申购/赎回时会带进来或带走一部分未分配利润，这部分记入损益平准金，避免把投资人的进出误算成基金的收益或亏损。答不出来时的安全说法："这个科目是用来在申赎时区分已实现/未实现收益归属的，具体规则我记得不够细。"

高结账流程是怎样的？结账后还能改数据吗？

结账一般包括：计提应计费用 → 结转损益 → 核对试算平衡 → 锁定会计期间。结账后通常不允许直接改数，需要走反结账 → 修正 → 重新结账的流程，并且要留痕。测试关注点：反结账的权限控制、反结账后再结账的数据是否一致、跨月/跨年结转是否正确。

高凭证重复生成，可能是哪些原因？

四类：① 业务数据重复导入（同一批数据跑了两遍，系统没做幂等）；② 跑批中断后重跑没有清理已生成的凭证；③ 触发条件重叠（两个规则都命中同一笔业务）；④ 并发——同一产品被两个任务同时处理。验证方法：按业务唯一键分组计数找 count > 1，再结合跑批日志定位。

测试与工具

必答账务模块的测试用例，你会怎么设计？

四层：

  • 规则层：每类业务的分录规则（借贷方向、科目、金额拆分），用判定表穷举规则组合。
  • 数据层：金额边界（0、负数、极大值）、精度（小数位、舍入）、数量边界。
  • 流程层：日终制证 → 过账 → 试算平衡 → 结账 → 反结账，用场景法串起来。
  • 一致性层：凭证 ↔ 明细账 ↔ 科目余额表 ↔ 报表 的四方勾稽；新老版本结果一致。

另外每个用例我都要能答出"正确答案从哪来"——手算、Excel、老系统、托管行，四条独立路径之一。

高你怎么验证账务算得对？

三方比对 + 逐层勾稽。三方比对：系统算 vs 手工 Excel 算、新版本 vs 老版本、我方 vs 托管行。逐层勾稽：业务流水 → 凭证明细 → 科目余额 → 报表，每一层都能往上追到源头。再加逐笔 SQL 校验：把凭证明细和业务明细按唯一键 JOIN 起来，逐笔比金额。

高你怎么区分前后端 bug？（一面问过，复试可能再问）

按"请求 → 数据 → 落库 → 日志"四层切：

  1. 看请求：F12 的 Network，请求发出去没有、参数对不对。没发出或参数错 → 前端。
  2. 绕过前端打接口：Postman 直接调。接口返回正确但页面显示错 → 前端（渲染/字段映射）；接口返回就错 → 后端。
  3. 查数据库：SQL 看落库。落库就错 → 后端；落库对但接口返回错 → 后端（查询/序列化）。
  4. 看日志：后端有异常堆栈 → 后端。

账务系统的特殊性：不能只看页面，要沿数据链路切——比如净值不对，可能是"行情数据错 → 计算错 → 展示错"，得逐层排。我习惯先判断问题出在哪一层，再决定找谁，这样能减少来回推诿。

高用过 AI 吗？怎么用在测试里？（一面问过）

三个场景：① 用例设计——把需求描述和业务规则给 AI，先出一版用例骨架，我再按业务经验补充裁剪；② 脚本生成——用 Cursor/Claude Code 生成 pytest 接口自动化和 Playwright UI 自动化脚本，我负责审查调试；③ 问题定位——把报错堆栈和 SQL 给它辅助分析。

但守住一条线：AI 生成的断言必须我自己复核，尤其是涉及金额和精度的。账务系统里的断言错一条，比少测十条更危险。

动机与稳定性（复试和 HR 面一定会再问）

必答你更想做业务测试还是开发？（一面问过，这是你的最大风险点）
为什么这题危险 你有开发能力，面试官会担心你把测试当跳板，干一年就转开发。而你还带着 gap 5 个月，越是急于入职，面试官越会怀疑投入度。这题的答案直接关系到"要不要给你发 offer"。

正确方向：明确选业务测试，并解释为什么开发是手段不是目的。

"业务测试。我做过全栈的工具开发，但我发现真正让我有成就感的，是把一个业务规则搞清楚、把数据验准，而不是写代码本身。

我写工具是为了解决测试里的重复劳动——比如我做配置生成工具、报文比对自动化，都是因为我在测试里被这些重复的活儿卡住了。所以我的定位是业务测试为主、具备测试开发能力，而不是随时准备转开发。

而且我理解账务模块恰恰需要这种人——它既要懂会计规则，又要能自己写 SQL 和工具去核对数据。这两样我都有。"

雷区答法（千万不要）："其实我更喜欢开发" / "两个都可以，看公司安排" / "先做测试，以后再看"——任何带"以后"的表达都会被听成"迟早要走"。

必答年底要去客户现场大概 2 个月，能接受吗？

明确接受，并且用事实而不是承诺来证明：

"可以。我在原公司参与过 6 个月的客户现场支持，那段时间是做版本升级、联调和 UAT 验收，包括现场和客户的业务人员一起对数据、跑流程。驻场的工作节奏、和客户沟通的方式我都是熟悉的。

而且我觉得账务模块去现场反而是好事——很多账务上的规则细节，合同和文档里写不清楚，只有跟客户的核算人员当面过一遍才说得明白。"

最后那句是你的加分项：它说明你理解"做账"这类业务的特殊性，而不是把驻场当成负担。

高期望薪资是多少？（一面问过，HR 面还会再问）

关键在于口径一致——一面报的数，HR 面不能变。

  • 如果一面报的是范围（如 15-18K）→ HR 面保持一致，说"和一面沟通的一致"。
  • 如果一面报的是单点数字 → HR 面可以小幅上浮，但要给理由："了解岗位职责后我发现要负责账务模块，对业务理解的要求比我想的更高。"
  • 如果一面没报（对方只说"后续沟通"）→ 先问区间："方便介绍一下这个岗位的薪资区间吗？"

被压价时的说法："我理解。想确认一下，这之外还有绩效、项目奖金或驻场补贴吗？另外调薪的周期和幅度大概怎样？"

中为什么选择做测试，而不是开发？

和"业务测试还是开发"是同一题的另一种问法，答案要一致。核心逻辑：我擅长的是"把规则搞清楚 + 把数据验准"这件事，而不是写代码本身。可以补一句真实感受："做测试的时候，我是站在业务的对立面去质疑它——这个过程我很享受。"

06复试的反问（换一批，别再问一面的）

一面你已经问过人流比、岗位归属、驻场安排。复试是更高级别的负责人，要问业务和团队层面的问题：

  • "账务模块目前是几个人负责？测试这边是和开发按模块结对，还是按版本轮着来？"
  • "估值核算 V5.5 信创版本在推进，账务模块的测试主要压力是在数据一致性验证上吗？"
  • "账务模块的历史缺陷，主要集中在哪一类？是凭证生成规则，还是结账和余额勾稽？"（这个问题很专业，能体现出你在思考质量风险从哪来）
  • "如果入职，您希望我在前三个月做到什么程度算合格？"
  • "年底这次去客户现场，主要是什么节点？我需要提前准备什么？"

07复试前 5 分钟速览

① 一句话定位（说给账务模块听的版本） "我是一个懂账务核对、能写 SQL 和工具、能把人工对账变成自动化的业务测试。我做的资金账务和贵司的估值做账，验证的是同一件事——业务数据被翻译成会计分录的过程，是否准确、完整、不重复。"
② 做账链路（能背出来） 业务发生 → 生成凭证 → 过账（明细账/总账）→ 试算平衡 → 期末结账 → 科目余额表 → 财务报表 → 估值表

测试重点在"生成凭证"这一环，因为它是业务规则到会计语言的翻译，最容易出 bug。

③ 三条铁律 有借必有贷，借贷必相等；资产 = 负债 + 所有者权益；期初 + 借方 − 贷方 = 期末。
④ 借贷不平的四类原因 单边分录 / 凭证重复生成 / 精度截断 / 期初未结转。
⑤ 最大风险题（必背） "更想做业务测试还是开发？" → "业务测试。开发是手段不是目的，我写工具是为了解决测试里的重复劳动。"
