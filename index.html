4.1 主项目：银企直联 DSP 渠道测试（完整版 2 分钟）

S · 背景（15 秒）

保融的资金管理系统是给寿险、财险、基金这些机构做资金结算的，上面对接 40 多家银行渠道。但银行之间的报文格式、前置机类型、证书、状态码都不一样，我们中间有一个 DSP 平台做统一适配：对上提供统一接口，对下适配各家银行。我负责的就是 DSP 渠道这条线的测试。

T · 我的责任（10 秒）

我要覆盖 40 多家银行渠道的接口测试，从升级、联调到验证上线全流程；同时负责渠道 7.0 升级到 8.0 这次大版本的回归验证。

A · 我具体做了什么（70 秒）

第一是接口与报文层面的验证。余额、明细、单笔和批量支付、查询、回单、退票这些接口，我会去分析 XML、JSON、Map 三种报文结构和渠道配置，判断问题出在银行的返回，还是我们的配置或映射。举个例子：有一次升级上线前，我发现某家银行交互的关键节点名称配置错了——这个节点直接决定报文能不能被对方正确解析，如果上线，客户的批量支付会全部失败。我在上线前把它拦下来了。

🔍 这个项目的高频追问与应答要点

报文比对平台的"忽略节点"是怎么设计的？

核心思路是把"每次都会变、但不代表业务出错"的字段"噪声"和"真正的业务差异"分开。具体做法：

  • 忽略规则配置化：按渠道 + 接口维度维护一套忽略路径清单（类似 JSONPath），比如时间戳、流水号、加密签名、随机数。不写死在代码里，配置改了不用发版。
  • 先全量比对再收敛：平台上线第一轮是全量比，把所有差异都列出来，我人工逐条确认——哪些是噪声、哪些是真差异。确认完把噪声沉淀成规则，下一轮就只剩真差异。
  • 规则要"从宽到严"逐步收紧：一开始忽略范围给大一点，先保证平台跑通；跑稳之后再逐条收紧，避免忽略掉真正的业务字段。

迁移到估值场景：估值表比对其实是同一套逻辑——估值表里也有很多与业务无关的噪声（导出时间、操作人、序号码），真正的比对项是科目代码、数量、成本、市值、估值增值、单位净值这些。我可以把这套"先全量、再收敛规则、按维度维护清单"的方法直接搬过来。

40 多家渠道，你怎么保证都覆盖到了？用例怎么组织？

两个层面：渠道维度的横向覆盖 + 业务维度的纵向覆盖。

  • 横向（渠道）：先做渠道分类，按报文格式（XML/JSON/Map）、接入方式（前置机/文件/直连）、支持的业务能力（是否支持批量、是否支持退票）打标签。同类渠道抽一家做深度测试，其余做同能力抽样 + 差异点专项。这样避免 40 家平均用力但其实重复。
  • 纵向（业务）：以接口为主干，每个接口覆盖正常流、异常流、边界值。比如"批量支付"要覆盖：单笔成功、批量部分成功、金额为 0、超限额、账户状态异常、银行超时无返回、重复提交。
  • 回归集：把跑一遍发现过问题的用例固化成"高价值回归集"，每次升级必跑；其余做成抽样回归。这就是那 1900 多条用例的组织思路。
你怎么确定一个差异是"系统的 bug"还是"银行返回的数据就是错的"？

三步定位，本质是往回追数据来源：

  1. 先看原始数据：把银行返回的原始报文/文件调出来，看报文本身是什么值。如果银行返回的就是错的，那问题不在我们。
  2. 再看解析与映射：如果报文没问题，就看我们 DSP 的解析和字段映射对不对，包括状态码映射表、金额单位（分/元）、字符编码。
  3. 最后看业务处理：如果解析没问题，再往上看资金系统的账务处理逻辑，用 SQL 查交易流水和状态字段，读 Java 代码看分支条件。

关键习惯是：在报 bug 之前先把"银行侧 / 我们侧"这个边界划清楚，这样开发不会来回扯皮，也能减少误报。这个习惯在估值场景同样适用——差异要先判断是行情源的问题、还是我们计算的问题。

7.0 到 8.0 升级回归，你要验证什么？

5.1 一句话理解估值核算

核心定义 估值核算 = 每天收盘后，把一只资管产品持有的所有资产按规则重新算一遍值多少钱，减去负债，得到"基金资产净值"，再除以份额，得到"单位净值"，并生成对应的会计分录、科目余额表、财务报表，最后和托管行核对、对外披露。

为什么它重要：单位净值直接决定投资者申购/赎回的价格。算错一分钱，就是投资者利益受损或不当得利，属于监管重点关注事件。所以这个系统对"准确性"的要求是金融系统里最高的一档，而且要求可追溯、可复核、可审计。

⭐ 高价值知识点：摊余成本法 + 影子定价（货币基金，必被问）

货币基金的资产以摊余成本法计价（不随市价波动），单位净值恒为 1.0000，投资者的收益通过每日结转份额实现。

但摊余成本法可能和真实市价产生偏离，所以每个估值日还要用市价重新算一遍，叫影子定价。

偏离度 = (影子定价 NAV − 摊余成本 NAV) ÷ 摊余成本 NAV

  • 负偏离度绝对值达到 0.25% → 管理人应在 5 个交易日内调整到 0.25% 以内
  • 正偏离度绝对值达到 0.5% → 需采取暂停申购等措施

测试点：偏离度计算的分母口径、阈值触发后的系统动作、连续多日的趋势判断。这是典型的"业务规则型"测试用例，最能体现业务理解。

5.5 估值系统的测试要点（把这一页当成明天的"方法论底牌"）

A. 数据准确性验证 —— 估值测试的第一命题

  • 三方比对：① 系统算的值 vs 手工 Excel 算的值；② 新版本算的值 vs 老版本算的值（升级/信创迁移场景）；③ 我方估值表 vs 托管行估值表。这三条正好对应你做过的"日志回放比对"，可以直接类比。
  • 逐层勾稽：交易流水 → 估值明细 → 估值表 → 凭证 → 科目余额表 → 财务报表 → 净值公告。任何一层对不上，都要能往上游追到源头。
  • 交叉复核：持仓数量和 TA 系统/券商对账单核对；资金余额和银行流水核对；份额和 TA 核对。

B. 精度与尾差 —— 最容易出"高级 bug"的地方

  • 净值精确到 0.0001 元，第 5 位四舍五入；要验证四舍五入的方向和累积误差。
  • 费率计提涉及除法，要验证中间过程是否保留足够小数位，避免"先舍入再计算"导致累计偏差。
  • 分红/结转份额场景下的尾差归属（尾差留给产品还是按持有人分摊）。
  • 金额单位（元/分）、多币种汇率换算的精度。

A 组 · 业务理解类（占比最高，务必过一遍）

必答你了解基金估值核算吗？说说你的理解。

用第 05.1 的流程图讲：三类数据接入 → 校验清洗 → 估值计算 → 费用计提 → 制证 → 科目余额和报表 → 估值表 → 与托管行核对 → T+1 披露。最后补一句自己的判断："这块我目前是自己系统看的资料，主干流程和核心公式我梳理过，但具体的业务细节肯定不如实际做过的人，需要到岗后补。"坦诚 + 有准备，是跨业务候选人的最优解。

必答基金资产净值和单位净值怎么算？

NAV = 资产总值 − 负债合计；资产总值 = Σ(持仓数量 × 估值价) + 银行存款 + 应收款等；单位净值 = NAV ÷ 总份额，精确到 0.0001 元，第 5 位四舍五入。可以补一句累计净值 = 单位净值 + 累计分红。

必答如果系统算出来的净值和托管行不一致，你怎么排查？

这题几乎一定会问，因为它是估值测试的日常。按"从大到小、从粗到细"的顺序：

  1. 先看差异的量级：如果差异很大（比如差几万），通常是漏记了某笔大额业务或某个科目；如果差异极小（0.0001 级别），基本是精度/舍入问题。
  2. 再定位到具体科目：比对双方估值表的每一行，找出是哪几个科目不一致。这一步就是我做的"估值表比对"。
  3. 按科目反推原因，常见五类：① 行情源不同（我方用中债、托管用中证，或者停牌股估值方法不同）；② 费用计提口径不同（计提基数、天数、费率起止日）；③ 场外数据未到位（场外基金净值 T+1 才公布，或非标数据管理人未及时提供）；④ 份额数据未同步（TA 数据未到或申赎确认延迟）；⑤ 精度处理不同（先后舍入顺序）。
  4. 最后落到验证：确认原因后要判断是系统 bug 还是数据时效问题。如果是 bug，用 SQL 从持仓明细往上追到凭证。

加分收尾："我做过渠道报文比对，这套'先看量级、再定位到明细、再反推原因、最后固化规则'的思路是一样的。而且差异原因一旦确认，我会把它沉淀成比对规则，下次同类差异自动识别，不用再人工判断。"

必答一只主动型股票基金的日终估值流程是怎样的？

照第 05.1 复述。重点突出：数据接入（含当日行情、当日交易、TA 份额）→ 校验清洗 → 计算市值 → 计提费用 → 结转损益 → 生成凭证 → 出具估值表 → 与托管行核对 → T+1 披露净值。

高货币基金为什么用摊余成本法？什么是影子定价和偏离度？

见第 05.3 的专条。核心三点：货币基金要求净值稳定（恒为 1.0000），所以用摊余成本法屏蔽市价波动；影子定价用来监控偏离；负偏离 0.25% / 正偏离 0.5% 的阈值和处置动作。如果记不清数字，就说"有明确的阈值和处置时限要求，具体数值我记得是 0.25% 和 0.5% 这两个档位"。

高管理费、托管费怎么计提？你觉得有哪些坑？

按日计提：每日费用 = 计提基数 × 年费率 ÷ 365（部分产品用 360，看合同）。

坑主要在四个地方：① 计提基数是当日 NAV 还是前一日 NAV；② 天数口径是自然日还是交易日，节假日是否计提；③ 费率是否分段（阶梯费率、有上下限）；④ 起止日期——产品成立首日、终止当日、暂停估值期间是否计提，以及费率变更的生效日切换。这些正好是"业务规则型用例"的典型。

高什么是估值增值？它是怎么产生会计凭证的？

估值增值 = 市值 − 成本总额，也就是浮动盈亏。它每天随行情变动，系统按"本次估值增值 − 上次估值增值"算出本期变动额，生成公允价值变动损益的凭证。测试关注点：估值增值的累计数和本期发生额能否对上、卖出后估值增值是否正确清零。

高分红有哪些方式？对净值有什么影响？

常见两种：现金分红（分红后单位净值下降，累计净值不变，投资人拿到现金）和红利再投（把分红按除息日净值折成份额，份额增加、单位净值下降）。货币基金还有"每日结转份额"。测试关注点：权益登记日 / 除息日 / 发放日的顺序，除息日净值是否正确下降，红利再投的份额计算精度，以及除息日当天又发生申赎时的口径。

高如果某只产品今天的净值出现异常波动，你怎么定位？

先按"是不是算错"和"是不是业务真实发生"两条路分。定位顺序：

  1. 看当日业务：有没有大额申赎、分红、大额交易？这些会让净值合法地跳变。
  2. 看行情：持仓标的是否有异常价格（停牌、退市、行情录入错误、价格单位错）。
  3. 看费用/损益：是否重复计提、跨期计提错误。
  4. 看份额：TA 份额是否同步错误（份额算错会直接让单位净值变形）。
  5. 落到数据层：用 SQL 逐层对账，从估值表追到凭证和流水。
高估值表里一般包含哪些内容？

五块：① 基本信息（产品代码/名称、估值日期、币种）；② 资产项目（银行存款、清算备付金、证券清算款、股票/债券/基金投资——分列成本、市值、估值增值，应收利息、应收股利等）；③ 负债项目（应付赎回款、应付管理人报酬、应付托管费、应付交易费用、应交税费等）；④ 所有者权益（实收资本/份额、未分配利润、损益平准金）；⑤ 关键指标（资产总值、负债合计、资产净值、单位净值、累计净值、份额）。

中T 日行情数据缺失会怎么处理？

系统一般用最近一次收到的历史净值作为当日行情，同时在估值表和净值公告上提示"部分标的未获取当日行情"。特殊日期（申赎申请日、业绩报酬计提日）如果行情未在约定时点前提供，会走异常流程，影响份额确认和赎回款交收进度。这属于典型的降级处理场景，测试要验证提示是否准确、降级逻辑是否可回溯。

中什么是损益平准金？为什么基金会计要有这个科目？

作用是区分"申赎带来的份额变动"和"投资产生的真实损益"。当投资人申购/赎回时，带进来或带走的未分配利润部分，记入损益平准金，避免把投资人的申赎误当成基金的收益或亏损。如果答不上来，就说"这个科目我记得是用来在申赎时区分已实现/未实现收益归属的，具体规则我记得不细"。

B 组 · 测试方法论类

必答给你一个"基金申购/赎回"功能，你怎么设计测试用例？

套第 05.5 的四步模板（定口径 → 造数据 → 列验证点 → 加异常）。展开：

  • 正常流：申购确认份额、赎回确认金额；不同金额档位、不同费率档位；不同渠道（直销/代销）。
  • 边界值：最小申购金额、等于最小金额、低于最小值应拒绝；赎回全部份额（份额归零）；持有天数恰好等于费率分界点（如第 7 天、第 30 天赎回费率不同）。
  • 业务规则：T 日提交用哪一天的净值（QDII 是 T+1 甚至 T+2）；确认份额的小数位；手续费的收取方式。
  • 异常流：金额超过账户余额、产品暂停申赎、非交易日提交、重复提交、募集期/封闭期。
  • 数据一致性：申赎后 TA 份额、估值表份额、总份额三者一致；N+1 日的净值是否正确反映。
必答用例设计方法有哪些？在估值场景怎么用？

等价类、边界值、场景法、因果图/判定表、正交实验、错误推测。估值场景的关键差异是要额外加一层"数据准确性"的验证设计，也就是每个用例都要想清楚"正确答案从哪来"。举例：费率档位用等价类 + 边界值；计提规则用判定表（基数 × 天数口径 × 费率类型组合）；日终流程用场景法；精度问题用错误推测（历史上出过的舍入 bug 沉淀成用例）。

高测试数据你怎么造？估值系统的数据造数难在哪？

分三层：基础数据（产品、账套、证券主数据）、业务数据（交易、持仓、行情、TA 份额）、结果数据（以便验证的期望值）。

难在三点：① 构造要"能被手工验证"——数据量不能大，一只产品、一笔交易、一条行情，这样正确答案可以手算；② 相互依赖——行情变了，市值、估值增值、净值、凭证全变，造数要成组造；③ 时效敏感——很多场景依赖"日期"，要能模拟非交易日、月末年末。

我的做法是用 SQL 造数 + Excel 建"期望值底稿"：造数脚本跑完，Excel 里用公式把期望净值算出来，再和系统结果比。这个习惯和我在资金项目里用 SQL 校验账务数据是一样的。

高接口测试你怎么做的？报文怎么校验？

三段式：① 接口文档与契约——先用 Postman 验证单个接口的入参出参、状态码、异常码；② 业务链路——串起多个接口验证端到端结果和数据的落库情况；③ 报文级校验——这是金融系统的特色，我做过 XML/JSON/Map 三种报文的比对，包括字段映射、金额单位、状态码映射，也做过日志回放 + 自动化比对，配置忽略节点过滤掉时间戳这类噪声字段。在估值场景，这套可以直接迁移到估值表比对和接口数据落库校验。自动化会用 pytest + requests 组织。

高一个版本要回归，你怎么保证覆盖率和效率？

核心是分层回归：① 必跑集——核心业务主干 + 历史缺陷用例 + 与本次变更强相关的用例，每次必跑；② 抽样集——按渠道/产品类型抽样；③ 全量集——大版本（如升级）才跑。同时用自动化覆盖可比对、可重复的部分（接口、报文比对），人的精力放在需要业务判断的部分。我在资金项目里维护 1900 多条用例就是按这个思路分层组织的。

高发现一个缺陷，开发说"这不是 bug，是设计如此"，你怎么办？

三步走，核心是把争论拉回到"依据"上：

  1. 先自证：再确认自己的理解对不对——查需求文档、产品合同、监管规定，看有没有明确口径。很多时候是需求文档没写清楚。
  2. 拉齐口径：把"依据"摆出来（业务规则、历史版本行为、同业做法、托管行的口径），和开发、需求一起对齐。如果确实是设计如此但会引发业务问题，就升级到需求方决策。
  3. 留痕：不管结论如何，都在缺陷单里记录结论和依据，避免以后重复扯皮。

补一句我的体会：在金融系统里，很多"设计如此"其实是"业务规则没被写清楚"。我遇到过一次类似情况，最后是拉着需求一起把规则明确下来，并且补了用例。

三个习惯：① 用例评审（自己先自查一遍再拉人评审）；② 做"反向检查"——不是从功能出发，而是从数据流向出发，把一份数据的完整生命周期走一遍，看哪个环节没被覆盖；③ 缺陷复盘——每个生产问题都问"为什么测试没发现"，然后补成用例。我维护的 1900 多条用例里就沉淀了不少这类"事后补的用例"。

高写一条 SQL：找出我方估值表和托管行估值表净值不一致的记录。 
SELECT a.fund_code, a.nav_date,
       a.unit_nav  AS our_nav,
       b.unit_nav  AS cust_nav,
       ROUND(a.unit_nav - b.unit_nav, 6) AS diff
FROM   t_nav_our a
JOIN   t_nav_cust b
  ON  a.fund_code = b.fund_code
 AND  a.nav_date  = b.nav_date
WHERE  ABS(a.unit_nav - b.unit_nav) > 0.0001;

加分说明："这里不用 = 比较，因为浮点数比较会有精度问题；也不能直接减完比较，要先用 ROUND 归一到业务精度。另外我还会加一个 FULL OUTER JOIN 的版本，把只有一边有的记录也捞出来——缺记录往往比数值不一致更危险。"

# 1) 只在一方存在的科目（缺项）
only = m[m["_merge"] != "both"]

# 2) 双方都有但金额不一致
both = m[m["_merge"] == "both"].copy()
both["差额"] = (both["市值_我方"] - both["市值_托管"]).round(2)
diff = both[both["差额"].abs() > 0.005]

with pd.ExcelWriter("比对结果.xlsx") as w:
    only.to_excel(w, sheet_name="缺项", index=False)
    diff.to_excel(w, sheet_name="金额差异", index=False)

这段代码可以现场讲，正好呼应你"报文比对自动化"的经历——思路完全一致：按业务键对齐 → 分"缺项"和"差异"两类输出 → 输出成可读的差异清单。

高跑批很慢，你怎么定位？

从外到内四层：① 先拆时间——在日志里打时间戳，看是数据接入慢、还是计算慢、还是制证/汇总慢；② 看数据量——是不是某个产品持仓特别多、行情数据量特别大；③ 看 SQL——慢查询日志，看执行计划，有没有全表扫描、缺索引、笛卡尔积；④ 看资源——CPU/内存/数据库连接数，是不是被并发任务抢了资源。我在原项目里参与过自动部署和平台维护，排查思路是先用日志定位到瓶颈环节，再往下钻。

中Linux 上你怎么查日志？

tail -f 实时跟、grep 按关键字/时间/错误码过滤、grep -C 看上下文、awk/sed 做切分统计。在 k8s 环境用 kubectl logs 看 Pod 日志，必要时 kubectl exec 进容器看。核心是先按时间定位到异常时间段，再按关键字缩小范围，最后看堆栈和上下文。

中你怎么用 AI 工具辅助测试？

三个用法：① 用例设计——把需求描述和业务规则给 AI，让它先出一版用例骨架，我再按业务经验补充和裁剪，效率能提升不少；② 脚本生成——用 Cursor/Claude Code 生成 pytest 接口自动化和 Playwright UI 自动化脚本，我负责审查和调试；③ 问题定位——把报错堆栈和 SQL 给它，辅助分析。

但我会守住一条线：AI 生成的用例和断言必须我自己复核，尤其是涉及金额和精度的断言，不能直接信。

8.1 "为什么从上一家离职？"

我在保融做了将近四年，收获很大，从功能测试一路做到能独立负责渠道线的测试和工具开发。离职主要是两个原因：一是我想换到深圳长期发展，这个决定和家庭规划有关；二是我希望往资管运营这条更核心的业务线深入——我原来做的是资金结算端，估值核算是资管运营里对业务理解要求最高的环节，我想往这个方向走。

8.2 "这 5 个月在做什么？"（必答题）

这段时间我主要做了三件事。

第一是完成了从杭州到深圳的搬迁和安顿，家里房子在收尾，需要有段时间处理。

第二是有意识地在补 AI 工程能力。这段时间我系统性地用 Claude Code、Cursor 这类工具做开发实践，也把接口自动化（pytest）和 UI 自动化（Playwright）重新梳理了一遍实战流程。因为我很确定下一份工作要往"业务测试 + 提质提效"的复合方向走，这一块是我主动去补的。

第三是求职和研究方向。我给自己定的方向很明确——继续做金融后台核心系统的测试，往资管估值这条线靠，所以这段时间也在看估值核算相关的业务资料。

✅ 这段话的设计逻辑 把 gap 从"空窗"改写成"能力保鲜期 + 方向确定期"。最关键的是最后一句——正好可以把话题引到第 05 节的估值知识上，让面试官觉得你不是在找工作，是在为这个岗位做准备。

场景话术

8.4 "能接受加班和驻场吗？"

可以。我在原公司参与过 6 个月的客户现场支持，那段时间是做版本升级、联调和 UAT 验收，包括现场和客户业务人员一起对数据、跑流程，对驻场的节奏和沟通方式我是熟悉的。上线期间和月末、季末这种高峰节点的加班，我也经历过——资金系统月末对账和版本上线经常要晚上跑，我是能适应的。

💡 关键技巧 不要只说"可以"，要说"可以，因为我做过，我知道是什么样"。前者是承诺，后者是经验。

8.5 "你的缺点是什么？"

我比较明显的一个问题是在业务细节的表达上不够精炼。我做事习惯把前因后果都讲清楚，给开发提缺陷的时候经常写得很长，好处是定位信息全，但有时候会让对方抓不住重点。
我意识到之后做了两个调整：一是提缺陷先写"一句话结论"，再展开细节；二是写报告会先列要点再补内容。现在反馈好了很多，但我觉得还可以再改进。

⚠️ 选择原则 缺点要满足三条：真实（不是"我太追求完美"）、不致命（不能是"我不细心"——测试岗最忌讳）、有改进行动。上面这个"表达不够精炼"就很合适，因为它同时还暗示了你的优点（信息全面、写得详细）。

8.6 另外三个要小心的坑

  • 不要贬低原公司或原业务。即使你很想转方向，也要说"资金结算这块让我打下了账务和数据验证的底子"。
  • 不要在业务术语上瞎编。编错一个词（比如把"摊余成本法"说成通用方法）比承认不会更致命。安全句式："这块我理解得不够细，我的理解是……，如果有偏差请您指正。"
  • 不要说"我什么都能学"。要说"我已经学了什么、还能学什么"，用事实替代态度。
